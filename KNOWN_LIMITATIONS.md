# Known Limitations — Monday Test Build

Honest, current-state list of what this build does **not** do yet, or does differently than it might first appear. Written as part of Sprint 5 ("Packaging"), branch `feature/tradingview-strategy-reconstruction`. Nothing here is a bug being hidden — each item is either a deliberate scope boundary (documented at the time it was made) or a structural gap this project has flagged since the moment it was found.

1. **No real underlying-index OHLC dataset exists in this repository.** `ReplayApplication`'s CSV driver (the thing that paces `ReplayEngine`'s candle loop) has only ever been fed a minimal placeholder in every sprint's testing, because `WeeklyFutureStage` never reads the driver CSV's own OHLC values — only the real `reference_inputs` (13-strike CE/PE first-candle data from `orb_levels.db`) drive its output. This means: Weekly Future/Strike Selection correctness has been validated against **real, live-captured data** (22/22 days, cross-checked against a second independent legacy implementation in `orb_summary`). The replay **candle-iteration mechanism itself** has only been exercised against placeholder/synthetic OHLC rows, not a real multi-candle trading day.

2. **Anchor strike (ATM) is caller-supplied, not derived.** No component in `src/` determines "today's ATM" from data — every sprint's testing has supplied it explicitly (from `orb_summary.atm`, itself a legacy-captured value). A live/replay run against a new day needs this supplied from outside the pipeline. This was flagged the moment `WeeklyFutureStage` was built and remains unresolved by design (guessing it would be inventing a business rule).

3. **Only one business engine is wired into the pipeline.** `WeeklyFutureStage` (wrapping `WeeklyFutureCalculator` + `StrikeSelector`) is the only registered `PipelineStage`. `QualificationEngine`, `TPEngine`, `StopLossEngine`, `TrailingStopEngine`, entry/winner/exit logic remain behind the six originally-blocked interfaces — still MISSING INFORMATION per this project's evidence-first discipline, not implemented, not stubbed with guessed behavior. Per the standing plan, these resume only once evidence exists, after Monday.

4. **"Execution Time" in the Replay Validation Dashboard is a candle-timestamp span, not a measured duration.** `application.replay_dashboard.ReplayDashboardRow.execution_time` is `max(candle_timestamp) - min(candle_timestamp)` for that day's candles — useful for spotting an unexpectedly short/long trading day in the *data*, not a real wall-clock measurement. Real wall-clock timing does exist elsewhere: `business.stage_diagnostics.StageDiagnostic` (per-stage, per-candle, real) and `tools/performance_benchmark.py` (per-replay, real, via `time.perf_counter` + `tracemalloc`).

5. **"Charts" in `TradingAnalysisDashboard` are structured data, not rendered pixels.** `build_chart_series` returns `(date, value)` point series — no charting or GUI library has been introduced anywhere in `src/`. Any real front end (or a script using matplotlib/plotly/etc.) can plot these directly; this codebase does not render an image or a browser view itself.

6. **CSV/Excel report writers do not auto-create their output directory.** Unlike `ReplayApplication.run()` (which does `mkdir(parents=True, exist_ok=True)` on its `output_directory`), the following raise `FileNotFoundError` if the parent directory doesn't already exist: `replay_report.write_report_csv`, `replay_dashboard.write_dashboard_csv`, `TradingAnalysisDashboard.export_csv`/`export_excel`, `regression_validator.write_regression_report_csv`, `performance_benchmark.write_performance_report_csv`. See `TESTING_CHECKLIST.md` §5.

7. **`orb_summary`'s legacy comparison values are floats with representation noise.** SQLite stores `fut_high`/`fut_low` as `REAL`; a value written as `24198.45` can round-trip as `24198.449999999997`. `tools/regression_validator.py` quantizes both sides to 2 decimal places before comparing — correct for this data, but worth knowing if you extend the comparison to a different precision.

8. **One dataset run is one session, regardless of how many calendar days it spans.** `replay.replay_engine.ReplayEngine` treats an entire `HistoricalDataset` as a single session/`ReplayResult`; per-day boundaries only exist at the *reporting* layer (`replay_dashboard`/`trading_analysis_dashboard` group by `candle_timestamp.date()` after the fact), not at the pipeline/session level itself. Every multi-day real-data run in this project's sprints has actually run one `ReplayApplication.run()` call *per day* and combined the resulting `ReplayResult`s afterward for reporting - not a single multi-day session.

9. **`tools/` is excluded from the 100%-coverage gate.** `pyproject.toml` scopes `[tool.coverage.run] source = ["src"]` — `tools/regression_validator.py` and `tools/performance_benchmark.py` have their own test suites (25 and 13 tests respectively) but are not held to the 100%-branch-coverage bar `src/` is.

10. **PR creation requires manual GitHub authentication.** `gh` (GitHub CLI) is installed in this environment but not authenticated — opening a pull request from this session requires running `gh auth login` first, or using the GitHub compare URL directly.

None of the above blocks Monday's testing of the replay platform itself — they are the boundaries of what "replay platform, one business engine, real-data-validated" currently means for this build.
